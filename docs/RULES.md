# Travel Memory 工程规则

## 产品边界

- Travel Memory 不只是帮助用户记录旅行，更重要的是帮助用户多年以后重新体验一次真实发生过的旅行。
- 不自动改写、补写或生成用户原话；`content` 属于用户的原始记忆。
- Journey、Timeline 和 Map 展示真实记录，不为叙事效果虚构内容。
- 地点推荐、搜索和地图选点只提供辅助信息；不得覆盖用户已确认或手动填写的地点名称。

## 代码与接口

- 不随意修改既有接口路径、请求字段、返回结构或错误语义；兼容性扩展优先采用新增字段或新增接口。
- 不做与当前任务无关的大范围重构，不为局部功能引入大型依赖或新的状态管理方案。
- 新增数据库变更必须提供独立、可审查、可重复执行的升级 SQL；不得通过修改初始化 SQL 影响已部署数据。
- Memory 坐标在数据库统一保存为 WGS84。高德地图和 POI 服务使用的 GCJ-02 坐标必须通过统一转换链路归一化，页面不得各自实现不同规则。
- 高德 Web Service Key 只能由后端使用；前端仅使用地图 JS API 所需的 Key 与安全配置，真实 Key 和安全密钥不得提交 Git。
- 多照片仍属于同一段 Memory，不为单张照片增加独立原话、时间或地点；图片顺序和主图必须保持一致。

## 数据与部署

- 禁止删除、重建或替换生产 MySQL volume。
- 禁止在需要保留数据的环境执行 `docker compose down -v` 或 `docker-compose down -v`。
- 生产 MySQL 版本变更必须先备份、核验版本和数据卷兼容性；不得原地跨大版本降级。
- `.env`、`.htpasswd`、备份、证书、私钥、真实密码和第三方 Key 不得提交 Git。
- 文件删除必须限制在配置的 uploads 根目录内，不跟随符号链接，并在删除前完成数据库引用保护和安全保留期判断。
- 生产环境首次启用孤儿图片清理必须使用 dry-run；确认候选统计正确后，才可单独评估真实删除。

## 验证要求

- 前端修改后执行 `npm run build`。
- 后端修改后执行 `mvn test`，或至少完成可验证的编译；涉及接口和坐标转换时应补充针对性测试。
- 上传、多照片、Timeline、Journey、Map、地点搜索与选点是核心回归链路；涉及其依赖配置时必须回归检查。
