# Travel Memory UI Guideline

## 设计目标

Travel Memory 不是旅行攻略、相册管理软件或后台管理系统。它是一册旅行回忆录：用户打开页面时，应感到自己正在重新体验一次旅行，而不是管理旅行数据。

所有设计围绕旅行、照片、故事和回忆展开。照片和用户原话优先，操作保持克制，移动端优先。

## 视觉原则

- 简洁、温暖、克制、沉浸，保留足够留白。
- Timeline 的照片应完整显示，不拉伸、不明显裁切；桌面端保持稳定的照片与文字列，移动端自然改为上下布局。
- Journey 必须自然支持横图、竖图和方图：横图不应占满屏幕，竖图居中保留原始构图，并使用页面纸张背景而不是播放器式画布。
- 多照片以主图和数量提示保持浏览节奏；点击照片进入统一图库，而不是在阅读页堆叠照片瀑布流。
- 不做后台管理感、密集表格、炫技动效或让按钮压过照片和原话的布局。
- 使用清晰的文字层级、轻阴影、适度圆角和可访问的颜色对比。

## 页面职责

### 列表

旅行列表用于进入不同旅行，突出封面、标题、目的地和时间，不承担复杂编辑工作。移动端标题使用“我的旅行记忆”，只保留一个清晰的新建入口；列表末尾使用“下一段旅程，正在路上”的轻量续写入口。卡片中的地点、日期和真实统计使用统一线性图标，背景和阴影保持接近白纸而不是厚重面板。

### 表单

创建和编辑页面用于低成本留下或修正记忆。字段保持必要，照片、原话、时间和地点优先，错误提示直接且温和。

地点搜索和地图选点属于表单的辅助流程：在独立弹窗或抽屉内维护临时选择，只有用户确认后才回填表单。官方地点名称是建议，不应覆盖用户的自定义地点描述。

Trip 的目的城市与 Memory 的精确地点分开处理。创建旅行时以城市搜索候选为主，地图仅用于确认大致中心；确认候选时同时保存解析出的国家和 WGS84 城市中心，旅行列表优先显示“国家 · 城市”。城市坐标只决定旅行地图的默认视野，不替代每条 Memory 自己的时间和地点。用户手动修改城市名称后必须同时清除旧国家和坐标，避免展示错误组合。

### Timeline

Timeline 是原始记忆记录页，按日期和时间组织 Memory，支持搜索、收藏、图库及必要的次级管理操作。原话和地点是信息主体，收藏与更多操作应保持弱化；日期只在分组标题出现，卡片时间轴只显示时分。

### Journey

Journey 是回放页，按日期和站点重新走过旅行。它强调地点、照片、原话和时间顺序；“下一站”仅作轻量分隔，不应出现编辑、删除、收藏或搜索等管理动作。

### Map

Map 用真实地图回答记忆发生在哪里。它以有坐标的记忆点和当前选中的记忆卡片为核心，不承担导航、路线规划或轨迹回放；没有坐标的记忆应得到温和说明。当整趟旅行尚无定位 Memory 时，可使用 Trip 的目的城市中心建立空间上下文，但不得把城市中心伪装成 Memory。地图展示页不直接编辑数据，坐标修正通过 Memory 表单中的选点流程完成。地图应保留高德要求的版权与审图信息，不用 CSS 隐藏。

## 布局与交互

- 不要求所有页面使用相同的 Header、Summary、Timeline 或 FAB 组合。
- 页面结构应服务于页面职责：列表便于扫描，表单便于填写，Timeline 体现连续时间，Journey 体现沉浸回放，Map 体现空间关系。

## 移动端视觉基准

- `docs/mobile-design/设计图` 中的十张 PNG 是核心页面的移动端布局基准，真实业务与权限边界优先于示例内容。
- 移动端页面内容宽度上限为 `430px`，常用水平留白为 `16px` 到 `18px`；卡片、地图画布和封面必须在 `390×844` 下无横向溢出。
- 页面标题使用适度的衬线字体建立回忆录气质，表单、按钮和辅助信息继续使用系统无衬线字体，不能让装饰文字降低可读性。
- 旅行上下文、账号菜单、旅行内导航必须复用共享组件，不允许各页面重新制作尺寸不同的图标、头像或标题条。
- 固定在底部的保存操作必须包含 `safe-area-inset-bottom`，更多菜单和账号菜单不得越过视口边缘。
- 设计图中的天气、分享、虚构数据和虚构人物不得作为纯视觉填充进入真实页面。
- 删除和高风险操作放在次级入口或确认流程中，不作为主视觉重点。
- 图片需要准确的 `alt` 文本；触控目标保持足够大小；加载状态优先使用稳定占位，避免页面跳动。

## 最终原则

每次 UI 变更前，确认它是否更像旅行回忆、是否突出照片和时间、是否减少操作负担、是否适配移动端。若页面更像管理系统，应重新设计。
